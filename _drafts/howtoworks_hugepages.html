PostgreSQL · virtual memory · TLB · huge pages

Your database owns 16 GB.
It is paying for it 300 times over.

Every PostgreSQL backend is a separate process, and every process keeps its own private page table describing the one shared_buffers region. Three hundred backends means three hundred descriptions of the same 16 GB — none of them shared, each one rebuilt from scratch, all of them costing real RAM. Here is exactly where that memory goes, and what a 2 MB page changes.

Source: Booster's Blog Postgres: huge_pages Kernel: HugeTLB
01 — THE COST

A page table is memory spent describing memory

Your program never touches a physical memory address. It uses virtual addresses, and something has to translate them. That something is the page table: a lookup structure, held in RAM, with one entry for every 4 KB page of address space the process can reach. The entries are small — 8 bytes each — but a 16 GB shared_buffers is ~4.2 million pages, and the arithmetic gets out of hand quickly.

4 KB at a time

The default page size on x86-64. Memory is tracked, mapped, and faulted in units of 4 KB — nothing smaller, and by default nothing larger.

8 bytes per entry

Each page needs one entry recording where it physically lives and what may be done with it. 4.2M entries × 8 B = 32 MB to describe 16 GB.

Once per process

And this is the part that hurts. The 32 MB is not paid once by the database — it is paid by every backend independently.

This is not theory you have to trust. The number is visible on any running server: VmPTE in /proc/<pid>/status is that process's page-table size, and PageTables in /proc/meminfo is the system-wide total. Everything on this page is an explanation of numbers you can read yourself in two commands.
02 — THE LOOKUP

Every memory access starts with a translation

The CPU caches recent translations in the TLB — a small, very fast hardware table. A hit costs essentially nothing. A miss sends the CPU walking a four-level tree in memory, several dependent reads deep, before the access you actually asked for can even begin. Step through both outcomes.

Step 1 of 5
TLB — hardware cache of translations PAGE WALK — four reads through the tree PHYSICAL ADDRESS
TLB reach is the number that matters. A core holds roughly 1500–2000 second-level TLB entries. With 4 KB pages that covers 8 MB of memory at once. With 2 MB pages the same entries cover 4 GB. A backend scanning a 16 GB shared_buffers falls off the edge of 8 MB constantly — and every fall costs a walk.
03 — THE ROOT CAUSE

PostgreSQL forks. Page tables do not merge.

A backend is a process, not a thread. All of them map the same physical shared_buffers, but each carries its own private translation structure describing it. Watch what happens when a second backend touches a page the first one has already faulted in.

Step 1 of 5
BACKEND — one OS process PAGE TABLE — private, ~32 MB SHARED_BUFFERS — one physical copy MINOR FAULT
A thread-based engine does not have this problem. One address space means one page table, shared by every worker. PostgreSQL's process model is what turns a fixed cost into a cost multiplied by your connection count — which is also why a connection pooler helps even if you never enable huge pages.
04 — FIRST TOUCH

The fault that has nothing to do with disk

When a backend touches a buffer for the first time, it takes a page fault even though the data is already sitting in RAM. Nothing is read from storage. The kernel simply fills in a missing entry in that process's table and lets the instruction retry. It is cheap individually and enormous in aggregate — roughly 42 million of them to warm ten backends against a 16 GB shared_buffers.

Step 1 of 5
Minor, not major. A major fault reads from disk. A minor fault only fixes up the page table — the physical page already exists. That is why this cost hides so well: there is no I/O wait to point at, no slow query to blame, just CPU time disappearing into the kernel a few microseconds at a time.

Real systems land below this ceiling. The explorer assumes every backend has read the whole pool. In practice a backend only allocates entries for pages it has actually touched, so its table grows with what it has read over its entire lifetime. Short-lived or narrowly specialised backends stay cheap; long-lived connections that query every table drift toward the ceiling.
06 — THE FIX

One entry for 2 MB instead of 512 entries

A huge page is not a different kind of memory. It is the same RAM, described in bigger units. The page table stops at the level above — one entry now covers 2 MB directly — so the leaf level disappears entirely, along with 511 of every 512 entries and 511 of every 512 faults.

There is a second, quieter win. Because a PMD entry covers exactly 2 MB — the same size as a huge page — processes mapping the same shared hugetlb region can under the right conditions share the PMD table itself instead of each keeping a private copy. Where that applies, one backend's page-table work becomes visible to the others. The conditions have shifted across kernel releases, so verify it on your own kernel by comparing VmPTE across backends rather than assuming.
Explicit, not transparent. Transparent Huge Pages (THP) are a different mechanism: best-effort rather than reserved. The kernel gives you huge pages when it can, may take them back later, and depending on your settings the work of producing them can cause latency spikes. The standard advice for databases is transparent_hugepage/enabled = never or madvise, with explicit hugetlb reservation via vm.nr_hugepages instead. Explicit reservation is a guarantee; THP is a probability.
07 — THE OTHER LEVER

A pooler attacks the other half of the multiplication

The cost is backends × shared_buffers ÷ page_size. Huge pages shrink the third term. A connection pooler caps the first one — and it needs no reboot, no kernel tuning, and no reserved memory.

the same shared_buffers underneath both500 clients through a pool of 30 produce 30 page tables, not 500. The overhead becomes a function of your pool size rather than of how many connections your application happens to open.

pool_size caps it

500 clients, pool_size = 30 → 30 backends. Roughly 960 MB of page tables instead of 15.6 GB.

Transaction mode

Server connections get reused far more densely, so each backend's working set stays hot and its translations stay resident.

server_lifetime

Recycling kills bloated backends and their page tables with them — but it throws away warm tables too. A trade, not a free win.

They are orthogonal. A pooler reduces the scale of the problem; huge pages reduce the cost per unit. Together, 30 backends at 64 KB each is simply not a number anyone needs to think about.
08 — RECAP

What to take away

The claimWhy it holds
Page tables cost real RAM8 bytes per 4 KB page. 16 GB of shared_buffers needs 32 MB of entries to describe it.
The cost multiplies by backendsEach process keeps a private table. Nothing is shared between them, so 300 backends means 300 copies.
Warm-up is not shared eitherBackend B faults on a page backend A already faulted in, because B's own table is empty there.
Huge pages remove 511 of every 512 entriesOne entry covers 2 MB instead of 4 KB. Same memory, 512× fewer descriptions of it.
It only matters at scaleSmall shared_buffers, few connections, or an I/O-bound workload — and none of this is your bottleneck.
Measure before and after. grep PageTables /proc/meminfo takes one second and answers the only question that matters: is this costing you hundreds of megabytes, or tens of gigabytes? Everything above is context for that one number.
